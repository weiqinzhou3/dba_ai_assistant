# 参考平台背景说明（Reference Platform Background）

## 1. 文档目的

本文件用于说明：

- 本项目为什么会参考一套历史企业数据库平台的资料
- 参考了哪些思想
- 哪些内容只是“背景来源”，不是实现依赖

## 2. 为什么存在“参考平台”

在本项目启动之前，已有一套企业内部数据库平台沉淀过：

- 资产管理模型
- 控制面与执行面分层
- 服务创建与变更流程
- 审批与任务状态管理
- 适配数据库、中间件与基础设施的能力

这些历史设计资料对本项目的价值不在于“直接复用其 Java 代码”，而在于帮助我们更快提炼企业级 DBA Assistant 所需的核心语义。

## 3. 本项目从参考平台中借鉴的内容

本项目主要借鉴以下设计思想：

### 3.1 资产先于执行

在企业场景里，不能让 Agent 直接面对：

- 裸 IP
- 裸 kubeconfig
- 裸数据库账号
- 裸 shell 权限

必须先有受控资产目录，再在资产之上执行动作。

### 3.2 控制面与执行面分层

需要区分：

- 谁负责接收请求、做编排、做审计、做审批
- 谁负责真正触达数据库/K8s/脚本/底层系统完成执行

### 3.3 工单/任务/子任务语义

企业级运维动作通常不是一个“立即执行”的简单 API，而可能是：

- 先创建变更申请
- 再审批
- 再执行
- 再查看任务状态
- 再回收执行证据

### 3.4 多执行通道适配

底层能力可能来自：

- 平台 API
- Kubernetes / 自定义资源
- 数据库直连
- gRPC 执行接口
- Shell / Ansible / Python

所以执行器必须可插拔。

### 3.5 基础审计思路

一次企业动作不仅需要知道“成功/失败”，还需要知道：

- 谁发起
- 对什么对象
- 做了什么
- 经过了什么审批
- 走了哪条执行路线
- 结果如何

## 4. 本项目不直接复用的内容

以下内容不作为本项目的直接运行时依赖：

1. 历史 Java Platform 的完整微服务体系
2. 其前端页面、网关、菜单体系
3. 其原有 URL/Method 级权限模型
4. 其已有但不完整的审批实现方式
5. 任何要求 coding agent“默认知道这个产品”的假设

## 5. 为什么正式 spec 不能依赖参考平台名词

因为 coding agent 默认并不知道：

- 这个参考平台是什么
- 某些专有对象名是否必须复用
- 某些流程是“必须兼容”，还是“仅供灵感参考”

因此，正式实现文档必须做到：

- 自解释
- 自包含
- 不依赖背景知识
- 不依赖私有产品名称

## 6. 推荐文档分工

### 面向实现的正式文档

例如：

- `00-project-context.md`
- `01-glossary.md`
- `03-assistant-spec-v0.1.md`
- `04-action-dictionary-v0.1.md`
- `05-control-layer-schema-v0.1.md`
- `06-rbac-model-v0.1.md`

这些文档必须：

- 不要求读者认识参考平台
- 用能力描述代替平台名词
- 所有术语都有定义

### 面向理解的参考文档

例如：

- 历史 PDF
- 历史设计手册
- 逆向分析报告
- 动作映射文档

这些文档用于帮助人类与 AI 理解设计来源，但不应该成为实现文档的唯一依赖。

## 7. 对 coding agent 的要求

当 coding agent 读取本仓库 docs 时，应遵循以下原则：

1. 以正式 spec 为准。
2. 参考平台资料只用于理解设计灵感。
3. 不默认假设参考平台运行时存在。
4. 不要求先接入某个历史 Java 平台才能实现系统。
5. 所有实现必须围绕本项目自己的 Control Layer、Action、RBAC、Audit、Adapter 模型展开。
