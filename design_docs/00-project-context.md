# 项目背景（Project Context）

## 1. 项目目标

本项目要建设的是一个**企业级 DBA Assistant**，而不是一个通用聊天机器人。

该 Assistant 的目标是：

1. 接收 DBA/平台工程师的自然语言请求。
2. 将请求转换为系统内部的标准动作（Action）。
3. 对目标资源进行识别、权限校验、风险判断与审批编排。
4. 通过受控执行路径完成真实运维动作。
5. 全程记录任务、审计与证据，确保企业可追踪、可复盘、可治理。

## 2. 上层智能体

本项目上层智能体计划使用 **Deep Agent**。

Deep Agent 在本项目中的职责是：

- 理解用户自然语言。
- 识别用户意图。
- 补全缺失参数。
- 组织多步计划。
- 调用高层 Skill。
- 将结果以自然语言返回给用户。

Deep Agent **不是最终执行权的持有者**。

## 3. 两类执行路径

系统必须兼容两类执行路径：

### 路径 A：MCP 模式

```text
Deep Agent -> MCP Server -> tools
```

适合场景：

- 企业内部已有 MCP Server。
- 平台团队已将部分能力暴露为 MCP tools。
- 希望 Agent 通过标准协议调用已有能力。

### 路径 B：自研受控执行适配器模式

```text
Deep Agent -> Assistant Control Layer -> Adapter -> Target System
```

Target System 可以是：

- 数据库直连接口
- Kubernetes API / 自定义资源
- gRPC 执行接口
- Shell / Ansible / Python 脚本
- 虚拟机场景下的 SSH / API

适合场景：

- 没有现成 MCP Server。
- 底层能力分散在数据库、K8s、脚本、平台 API 中。
- 需要更强的权限、审批、审计和执行控制。

## 4. 核心架构原则

本项目必须采用**分层架构**，以兼容性和复用性为优先目标。

核心原则如下：

1. **Agent 与执行权分离**：Deep Agent 负责理解和规划，不直接持有最终执行权。
2. **控制层独立**：所有权限、风险、审批、审计、证据都由 Assistant Control Layer 统一收口。
3. **动作统一**：系统内部使用统一动作字典（Action Dictionary），不直接把底层 controller/path/tool 名称暴露给 Agent。
4. **执行器可插拔**：MCP、数据库直连、K8s、gRPC、脚本等都通过 Adapter 层接入。
5. **资产先于执行**：所有执行动作都必须先命中受控资产对象，不能直接面向裸 IP、裸 kubeconfig、裸数据库账号。
6. **审批先于高风险执行**：高风险动作默认需要审批，不允许由 Agent 直接越权执行。

## 5. 一期首个 MVP 动作

一期建议先实现以下 MVP 动作：

- `mysql.database.create`

业务含义：

- 在一个**已纳管**的 MySQL 服务目标上创建逻辑数据库。

这是一条适合作为 MVP 的动作，因为：

1. 业务价值直接。
2. 输入输出相对清晰。
3. 可验证性强。
4. 容易形成“权限 -> 审批 -> 执行 -> 审计 -> 证据”的完整闭环。

## 6. 一期不追求的内容

v0.1 阶段不追求：

- 自动无人审批执行高风险变更。
- 一次覆盖所有数据库和中间件。
- 重建完整企业平台 UI。
- 替代现有所有运维平台。

## 7. 本项目中的“参考平台”说明

本项目参考过一套既有数据库平台的历史设计资料和代码逆向结果，用来帮助提炼：

- 资产管理思路
- 控制面与执行面分层思路
- 工单 / 审批 / 任务 / 子任务语义
- 审计与执行适配思路

但本项目：

- **不直接依赖该平台的 Java runtime**
- **不假设 coding agent 认识该平台**
- **所有正式实现文档必须自解释、自包含**
